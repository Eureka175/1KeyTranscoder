**Status: FIXED and REGRESSED. Fixture content unchanged.**

This record closes the line-ending defect that the P3–P4 documentation
consolidation exposed when it read the pushed fixture back from GitHub
(`docs/audio-sync-p4/known-limitations.md` §7, now marked resolved).

## 1. What was measured

The same CSV is materialised two ways, and the two are **not** byte-identical:

```text
                             size     CRLF   raw byte sha256
worktree (core.autocrlf=true)  55123   549   36242616062FFEC24F93062F6405273E9E12E90069ABA1FA50BFB4257306E2AF
committed blob / on GitHub     54574     0   7B1FB2DCAEECBA4BD170973C336F470D0E7B6746A551E41A88D9032D3A6B464B
difference                       549   549   = exactly 549 CRLF -> LF conversions
```

Both were read directly: the worktree with `read_bytes()`, the stored form with
`git cat-file blob HEAD:tests/fixtures/channel_sync/a7m5_real_137_baseline.csv`
(the blob object id is `76b702cc0150e956432b6935eefecd94b1a98d1e`).

**Normalising line endings makes them identical:**

```text
canonical_content_sha256(worktree) = 7B1FB2DCAEECBA4B…6E2AF
canonical_content_sha256(blob)     = 7B1FB2DCAEECBA4B…6E2AF
                            agree  = True
```

So **the fixture's content did not change.** What changed between the two
representations is the line terminator byte pattern and nothing else.

For the stored form the normalization is a no-op (it is already LF), which is
why the canonical digest and the stored blob's raw digest coincide **for this
file only**. They remain separately named constants because they answer
different questions.

## 2. Why the previous hash depended on CRLF

`core.autocrlf=true` (a common Windows default, and the setting on this machine)
makes git write CRLF into the working tree while storing LF in the object
database. The P4.2/P4.3/P4.4 audit harnesses hashed **the working-tree file**:

```python
RECORDED_SHA256_PREFIX = "36242616062FFEC2"      # removed by P4.5
got = sha256_file(BASELINE)                      # raw bytes as checked out
if not got.startswith(RECORDED_SHA256_PREFIX):
    print("ABORT: the frozen fixture does not match its recorded hash.")
    return 4
```

`36242616062FFEC2…` is the raw digest of the **CRLF** representation. It is the
correct description of the bytes those runs actually read on this machine, and
it is the value published in `docs/hardware-decode/final-report.md` HD-G06. It
was **not** a number error; it was a *scope* error: a packaging difference was
being reported as an integrity failure.

Consequences: on a clean Linux/macOS checkout — or any blob-level read — the
comparison failed and the audit aborted with exit 4. Fail-closed, but for the
wrong reason, and it made the recorded P1/P4 results read as
platform-independent when they were not.

`.gitattributes` already contained a rule written for exactly this failure mode
(`*.patch text eol=lf`, with the rationale that `core.autocrlf=true` "silently
changed the patch hashes and made … fail on a clean checkout"). The frozen CSV
had no such rule: `git check-attr -a` on it returns **nothing**.

## 3. The hash contract

Two identities, named separately and never conflated:

| name | what it identifies | line-ending dependent? | used for pass/fail? |
|---|---|---|---|
| `raw_byte_sha256` | the bytes exactly as read | **yes** | **no** — reported for provenance only |
| `canonical_content_sha256` | the bytes after normalization | **no** | **yes** — the acceptance test |

```text
hash_algorithm   : SHA-256
normalization_id : sha256-lf-normalized-v1
rule             : b"\r\n" -> b"\n", then any remaining b"\r" -> b"\n"
                   no other byte is added, removed, reordered or ignored
```

The rule is deliberately minimal. It does **not** strip whitespace, drop a
field, re-serialise the CSV, reorder columns, add or remove rows, or ignore
trailing content — so a real data change still changes the canonical digest.
Verified, per mutation, in §5.

### The historical raw digest is retained, not replaced

```text
RAW_BYTE_SHA256_BY_LINE_ENDING = {
  "crlf": "36242616062FFEC2…306E2AF",   # this machine's checkout
  "lf":   "7B1FB2DCAEECBA4B…6E2AF",     # the stored/GitHub form
}
RECORDED_RAW_PREFIX_HD_G06 = "36242616062FFEC2"   # kept verbatim
```

`RECORDED_RAW_PREFIX_HD_G06` is kept **verbatim and unedited**. No document was
changed to imply that the bytes the earlier experiments read were different from
what they read. `docs/hardware-decode/final-report.md` HD-G06 was **not**
touched: its recorded value remains the historical observation of a CRLF
checkout.

## 4. Implementation

Two files, both **tracked** (a contract that must reproduce from a clean GitHub
checkout cannot live under the git-ignored `work/` tree):

### `tests/audio_sync_p4/baseline_identity.py`

The contract: the versioned normalization, the two digest functions, the
expected canonical digest, the historical raw digests, the structural
invariants, and `check_baseline()` — a fail-closed identity check returning a
structured verdict.

`check_baseline()` returns `ok=True` **only** when the file is present,
readable, non-empty, canonically identical to the expectation, and structurally
intact. A missing file, an unreadable path, an empty file, and a wrong
expectation are all failures with populated `problems`.

Structural invariants are checked **independently of the digest**, so a
normalization bug cannot by itself make a wrong file look right:

```text
header / column order   : the 17 frozen field names, in order
data rows               : 548        (549 lines including the header)
fields per row          : 17
encoding                : pure ASCII, 0 quote bytes
```

The last two are what make a line-ending-only rule *exact* for this file: with
no `"` quoting, no `\r` byte can occur inside a field, so normalization can only
ever rewrite terminators. That precondition is asserted, not assumed.

### `tests/audio_sync_p4/test_baseline_hash_portability.py`

The permanent regression. **65 cases, 10 controls, 0 FAIL, 0 skipped.**

### The three local audit harnesses

`work/p4.2/`, `work/p4.3/` and `work/p4.4/`'s `p1-audit/audit_baseline.py` now
import the tracked contract instead of carrying their own copy:

```python
from tests.audio_sync_p4 import baseline_identity
ident = baseline_identity.check_baseline(BASELINE)
```

They print the raw digest, the checkout form, the canonical digest, the expected
canonical digest, the normalization id, and the historical raw prefix — so the
distinction is visible in their own output. **Exit-code semantics are
preserved:** a genuine mismatch still aborts, P4.2's absent fixture still
returns 3, mismatch still returns 4, and the audits still refuse to conclude
anything from a fixture they cannot identify.

These files are **git-ignored and local-only**. Fixing them is not a pushed
feature fix; the pushed, reproducible artefact is the tracked regression above.
They are named here so the two are not confused.

### Not changed

`tests/hwdecode/harness.py` HD-G06 needed **no** change. It computes the digest
as *evidence* (`ev["baseline_sha256"]`) and verifies the fixture via
`git diff --name-only main...HEAD -- tests/fixtures/channel_sync/`, so it was
never line-ending sensitive. Its recorded value in
`docs/hardware-decode/final-report.md` is an observation printed by that run.

## 5. Regression: what the 65 cases establish

| section | establishes |
|---|---|
| **A** (8) | the real fixture: raw digest matches the bytes on disk; canonical digest matches the constant; 548 rows / 549 lines / 17 fields; 0 quotes; 0 stray CR; worktree and stored forms share one canonical identity |
| **B** (13) | CRLF ≡ LF. The two forms really are different byte strings (55123 vs 54574, delta 549 — non-vacuous), yet their canonical digests are equal and equal to the constant. Also: mixed endings, lone-CR (classic Mac) endings, idempotence, identity on already-LF input, and that the only size change is one byte per CRLF |
| **C** (12) | a real content change is **still** detected: one digit changed, a decision word changed, a filename changed, a trailing space added inside a field, a row removed, a row duplicated, two rows reordered, two header columns reordered, the final newline removed, a blank line prepended, and a content change combined with a line-ending change |
| **D** (9) | fail closed: missing file, unreadable path, empty file, newline-only file, truncated file, truncation at a clean line boundary (caught by the row-count invariant), a wrong expected digest, and a wrong expectation over otherwise-good content |
| **E** (5) | the two identities are distinct exported constants; the historical HD-G06 prefix describes the **CRLF** form and does **not** match the LF form |
| **F** (8) | no consumer re-introduced a raw-byte acceptance test: the three local harnesses import the contract; the tracked HD-G06 pins no raw digest; the contract lives in the tracked tree |

The 10 controls each fail on deliberately broken input, so none of the above is
vacuous. The two that matter most:

* **the raw-byte contract really is line-ending dependent** — a check asserting
  `raw(crlf) == raw(lf)` fails, which is the original defect reproduced;
* **without the CRLF rule the two forms are not equal** — an identity
  "normalization" fails, so §B's equality comes from the rule and not from the
  inputs happening to match.

`B` and `C` are a deliberate pincer: `B` requires CRLF and LF to be *equal*,
`C` requires real content changes to be *unequal*. A "fix" that over-normalised
would break `C`; a "fix" that kept hashing raw bytes would break `B`.

## 7. Windows / LF compatibility

The contract is now checkout-form agnostic. Verified behaviour:

| environment | raw digest | canonical digest | audit verdict |
|---|---|---|---|
| this machine, `core.autocrlf=true`, CRLF checkout | `36242616062FFEC2…` | `7B1FB2DCAEECBA4B…` | **accept** |
| clean LF checkout / blob read | `7B1FB2DCAEECBA4B…` | `7B1FB2DCAEECBA4B…` | **accept** |
| any real content edit | differs | **differs** | **abort (exit 4)** |

To reproduce on a clean LF checkout:

```powershell
# materialise LF without touching this working tree
git -c core.autocrlf=false worktree add --detach <path> HEAD
python tests/audio_sync_p4/test_baseline_hash_portability.py
```

The tracked regression is self-contained and needs only the repository, so it
runs unchanged on Windows and on Linux/macOS. The three `work/` harnesses are
local-only by design and are not part of the reproducible artefact.

The fail-closed behaviour is **retained**: a real content change still produces
`ok=False` and exit 4. What is no longer treated as an integrity failure is a
line-ending difference, because it is not one.
