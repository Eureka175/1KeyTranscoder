# P4.3 — Production Semantics Decision Closure

**Status: D1 DECIDED AND IMPLEMENTED. D2 and D5 `DEFERRED` with an explicit,
versioned implementation default. D8 STATE DEFINED. No algorithm changed.**

This phase answers one question:

> once the evidence semantics are correct, what is the *production contract*?

It is not algorithm development. `core/sync_estimate.py`, GCC-PHAT,
`core/sync_fix.py`, the P1 correction math and the six-pair E2E correction
mechanics are **unchanged**. Drift correction, resampling and adaptive
measurement were not started. The diff is classification, plumbing and
declaration.

## D1 Evidence Contract

### Decision

```text
DECIDED: the production sync result states the evidence that justifies its value.

Population: MEASUREMENT FRAMES of the estimate that produced the value.
    (NOT plan windows, NOT residual-grid points — three different denominators,
     and d1-uncertainty-contract.md section 4.2 forbids naming one for another.)
```

### What was wrong

The evidence existed, was computed, gated the adoption — and then stopped at
the producer's own report row. Traced by execution, not inspection:

```text
core/channel_sync.py            rows[i]["evidence"] = {usable_frames, total_frames,
                                                       coverage, confidence}   (P4.2)
        |  DROPPED: ChannelSyncReport.resolve() had no field for total_frames or
        |           coverage, so 2 of the 4 evidence facts died here
AudioSyncResult                 usable_frames, quality, reason        (+ nothing else)
        |  DROPPED: AudioTrack.refresh_sync() aggregated status only
AudioTrack                      sync_status, sync_offset_samples, sync_offset_ms
        |  DROPPED: AudioChannelRef carried the same three scalars
AudioChannelRef -> AudioPlan -> production/output.py
                                offsets[channel] = offset,  statuses[channel] = "success"
```

A consumer at the end of that chain could see `status = "success"` and a number,
and nothing that could contradict either.

### What P4.3 implements

| object | added | default | why it is needed |
|---|---|---|---|
| `AudioSyncResult` | `total_frames: int\|None` | `None` | `usable_frames` without its denominator is uninterpretable: 5 frames is either plenty or fatal |
| `AudioSyncResult` | `coverage: float\|None` | `None` | stated, not re-derived — two consumers dividing independently is how two denominators appear |
| `AudioSyncResult` | `measurement_coverage` *(property)* | — | one read-only entry point: stated value, else derived, else `None` — **never 0** |
| `AudioTrack` | `sync_coverage: float\|None` | `None` | aggregated **min over channels**: one under-measured channel must not be averaged away |
| `AudioChannelRef` | `sync_coverage: float\|None` | `None` | the product-facing traceability record |
| `AlignmentOutcome` | `evidence: dict` | `{}` | `offsets` says *how much*; this says *how well measured*, per channel |
| `ChannelSyncReport` | `evidence_gate: dict` | read from the report, else `effective_opts` | a consumer must judge the row by the gate that **produced** it |
| `channel_sync` report | `"evidence_gate"` key | always written | so an `opts` override cannot be re-interpreted by the default thresholds |

`usable_frames` already existed. The names match
`core.audio_sync.PairSyncEstimate` exactly, which already carried
`usable_frames` **and** `total_frames` — the same measurement fact is not
allowed two names in two sync models.

**Not added, deliberately:** `measured_windows` / `total_windows` / `policy`
(the plan-window population). The only object that can count plan windows is
`core/audio_sync_tv.CorrectionPlan`, and it is imported by **no** production
module. A field nothing can populate is decoration, and it would collide by name
with the frame-domain `coverage`. Recorded as open, with its unblocking
condition, below.

### The invariant, and how it is enforced

```text
I1  SUCCESS  =>  the production evidence gate is satisfied
I2  LOW_CONFIDENCE  =>  a numeric estimate MAY exist, and is not trusted
I3  SUCCESS and "insufficient evidence" must never both hold
```

Enforced in three places, each with a different job:

1. **The producer** (`core/channel_sync.py`, P4.2): a `fixed` row cannot be
   written unless the adopted estimate passed the gate.
2. **The resolver** (`core/audio_models.ChannelSyncReport.resolve`): a row that
   asserts `decision="fixed"` **while stating** coverage below the gate is
   downgraded to `LOW_CONFIDENCE` with reason `evidence_insufficient` — the
   reason code P4.2 already added, mapped to the member that already meant
   "a number exists and is not trusted". **No new `SyncStatus` member.**
3. **The apply gate** (`core/audio_timeline._effective_offset`): returns 0
   unless the status is `SUCCESS`, so the number is not erased but is not
   applied either.

The resolver's guard is deliberately narrow. It fires only when the row
**states** a coverage. "Not stated" is `None`, and `None` asserts nothing:

```text
a historical row with no coverage field  ->  unchanged (still SUCCESS)
a row stating coverage below the gate    ->  LOW_CONFIDENCE  (contradiction)
```

That is what keeps the addition **backward compatible** while still removing
the failure mode. `tests/audio_sync_p4/test_production_semantics.py` S5.4 and
S5.5 assert both halves, and S5.5 asserts the gate is **read from the report**
by feeding the same row under a stated laxer gate and observing acceptance.

### The second live instance of the defect family (found and fixed here)

The P4.3 static family audit searched the production consumers for the shape

```text
a sync VALUE exists  ->  the code corrects / publishes it
                         without a status or evidence check
```

and found a **second live instance**, in a different file:

```text
core/audio_sync.py :: _estimate_one          (the P2 alignment path)
    _ESTIMATE_DEFAULTS had NO `min_usable_fraction` key at all
    it gated usable_frames and confidence, then set status = "success"
    while its own docstring claimed "与文件级管线同一套质量门"

production/output.py :: apply_alignment
    status == "success"  ->  out.offsets[channel] = offset_samples
                         ->  apply_sync_result writes it into the plan
```

Reproduced **by execution**, against the real production entry point
`production.output.apply_alignment`:

| | before | after |
|---|---|---|
| measurement | `usable_frames=8/39 coverage=0.205 confidence=0.996` | same |
| published status | `success` | `failed` |
| offsets written | `{'rec:s0:c0': 480.0}` | `{}` |
| applied | `1` | `0` |
| control (full signal, coverage 0.949) | `success`, offset 480 | `success`, offset 480 |

The harness is identical in both runs; the "before" run was executed against the

(`work/p4.3/repro/repro_p2_gate.py`, `--expect defect` vs `--expect fixed`.)

The fix: the third gate is added, and the two gate sets are **cross-checked at
import time** (`_assert_gate_matches_production`), so the comment "same

untouched (section **Default Path Protection**). Recorded as a deliberate
behaviour change, not as a silent fix.

## D2 — Gap Policy

```text
DECISION:  DEFERRED
implementation default:  "hold"      (core/audio_sync_tv.DEFAULT_POLICY)
semantic contract:       not frozen
```

### Why it cannot be decided from the existing evidence

P4's own matrix is the answer, and it is a negative result:

```text
NO COLUMN DOMINATES.
Each candidate is the better answer in a different row, and the rows that
separate them are decided by the position of a discontinuity inside the gap —
which is NOT OBSERVABLE.
```

Concretely, from `gap-policy-decision.md` §4 and P3.6:

* a hidden discontinuity costs the full step under **every** carry policy;
* `linear` halves it when the discontinuity is mid-gap and **doubles** it at the
  closing edge — so the sign of `linear`-vs-`carry` depends on an unobservable;
* `hold` repeats a measured value (stale by construction, and the staleness is
  not measurable from inside the gap);
* `no_correction_gap` asserts nothing about the material, needs no context at
  all — and is very close to a no-op, deciding whether most of the stream is
  corrected **at all**;
* `explicit_state` produces **bit-identical PCM to `hold`** and differs only in
  what it claims;
* `current`'s state machine is correct in 132/132 cases; what fails is the
  separate `resolved` claim (1/22) — a semantic over-claim, not an algorithmic
  error, and it is **not** described here as algorithmically wrong.

The question P4 could not answer, in P3's words:

> whether uncorrected alignment inside a gap is worse than invented structure.
> That depends on what the audio is for, and a concert master and a
> sync-reference track do not want the same answer.

That is a product statement, not an engineering one. P4.3 does not make it.

### What P4.3 does instead

1. Records the decision as **machine-readable**, with the default and the
   contract as **separate fields** (`core/audio_sync_tv.DECISION_STATUS`):

   ```python
   "implementation_default": DEFAULT_POLICY,       # "hold"
   "semantic_contract":      "DEFERRED",
   "why_deferred":           "...",
   "unblocked_by":           "a product statement of what the output audio
                              is for, plus a residual budget per state (D3)",
   ```

2. Asserts the separation in the suite (S10.4), so changing the default without
   changing the record fails a test rather than silently settling a decision.

3. Keeps `UNRESOLVED_GAP` **statable and unattributable to a measurement** —
   already true since P3/P4, re-asserted (S3, S8) and re-measured on real
   material (below).

## D8 — Enablement

### The state, stated precisely — because "Audio Sync" names three things

| path | entry point | state today | who turns it on |
|---|---|---|---|
| **P1** `core/channel_sync.py` — per-track fixed offset | the production pipeline, via `opts["channel_sync_*"]` | **implemented, gated** | the caller's options; not changed by P4.3 |
| **P2** `core/audio_sync.py` — constant per-channel offset | `production/output.py::apply_alignment` | **reached through `--audio-plan`; within an opt-in request, `auto` enables it for all-PCM sources** | explicit opt-in at the file level (`--audio-plan`, documented *"默认不启用"*) + an explicit `sync.reference` (never guessed) |
| **P4** `core/audio_sync_tv.py` — time-varying per-window correction | *(none)* | **OFF — structurally** | nothing: no production module imports it, asserted by test |

```text
DEFAULT PRODUCTION PATH: UNCHANGED.
    no --audio-plan  ->  audio is handled exactly as before (-map 0 + -c:a copy)
    the P4 time-varying path is not merely disabled — it is unreachable.
```

### Safety contract

```text
evidence insufficient          ->  an explicit NON-SUCCESS state
                                   (LOW_CONFIDENCE / failed — never a silent guess)
value present, status trusted  ->  the only combination that corrects
decoder / PCM / timeline cannot consume the result
                               ->  FAIL CLOSED (a stable reason code, and the
                                   source audio is left untouched or the file is
                                   copied through byte-for-byte)
```

The time-varying module's own error contract is narrower and unchanged from P4:
a **missing policy context** is an `AudioSyncError` (raise, never guess), while
`UNRESOLVED_GAP` is a **valid state that never raises**. Uncertainty is not
error; an invalid execution is.

Enablement itself (`D8-C`, default ON) remains **not taken**: it requires D2 and
D5, which are `DEFERRED`.

## State Machine

One table, in production code (`core/audio_models.SYNC_STATUS_PATH`), because
every consumer that has to guess "does success mean trusted?" is a place the
contract can be lost.

| status | value trusted | may enter correction | unresolved |
|---|---|---|---|
| `not_processed` | no | no | no |
| `not_applicable` | no | no | no |
| `success` | **yes** | **yes** | no |
| `already_aligned` | yes | no¹ | no |
| `low_confidence` | no | no | no |
| `non_constant` | no | no | no |
| `out_of_range` | no | no | no |
| `recheck_failed` | no | no | no |
| `failed` | no | no | no |

¹ not a distrust: there is no correction to apply. It is "measured, and the
measurement says nothing needs moving".

Three asserted properties (suite SM.1–SM.4):

```text
every member has exactly one row
nothing may enter the correction path unless its value is trusted
no state is simultaneously trusted and unresolved
SUCCESS is the ONLY correcting member
```

The last one is the point: `offset exists -> corrected` has exactly one key, and
that key is the one the evidence gate guards.

The per-window state machine from P4 is separate and unchanged:

```text
TRUSTED ──refused──▶ UNRESOLVED_GAP ──trusted measurement returns──▶ REENTRY ──▶ TRUSTED
state[i] = f(resolved_mask, i)          # a pure function; no chunk history
```

## Consumer Contract

What must survive, where it may stop, and what was proven rather than argued:

| boundary | evidence must survive? | how it is asserted |
|---|---|---|
| `channel_sync` report row | yes | `rows[i]["evidence"]` on every decision row (P4.2) |
| `ChannelSyncReport.resolve` | yes | S1.3, S2.3 — coverage + denominator reach `AudioSyncResult` |
| `AudioTrack.refresh_sync` | yes, **conservatively** | C.2, C.3 — the track reports the **worst** channel, not the average |
| `AudioChannelRef` → dict | yes | C.4 — round-trips exactly, `None` stays `None` |
| `AudioPlan.sync_of` | yes | `coverage=ref.sync_coverage` |
| `AlignmentOutcome` | yes | `evidence[channel]` with `evidence_sufficient` |
| `ChannelTimeline.offset_samples` | **NO — this is the safe termination boundary** | EX-1: a `LOW_CONFIDENCE` channel reaches the PCM layer as `offset_samples=0` while `raw_offset_samples=480.0` is still recorded |
| `AudioInputRef` (PCM / composition) | no | C.5 — asserted state-free, so a future change that pushes state **down** is caught |

```text
the contract pushes uncertainty UP (into the model, the report, the log)
it does not push it DOWN (into execution)
```

`ChannelTimeline` is the one place where a resolved integer is the **correct**
interface (`d1-uncertainty-contract.md` §5, consumer class B). P4.3 verified
that by execution rather than by reading: the gate
(`core/audio_timeline._effective_offset`) runs at resolution time, so the mixer
never sees an ungated number. That closes the three most alarming static
findings (`core/audio_mix.py:675`, `:775`, `core/audio_route.py:207`) as
**not the family**, with a control proving the same channel *does* reach the
mixer when its status is `SUCCESS`.

Logging: a corrected track that is not fully measured produces a line naming its
coverage (`production/output.py`). A run that logs only `applied` has
reproduced the D6 defect in the log.
