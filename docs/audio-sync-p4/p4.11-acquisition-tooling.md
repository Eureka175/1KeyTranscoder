# P4.11 — Acquisition Tooling & End-to-End Preflight

**Purpose.** P4.10 established that no source on this machine carries an independent
delay truth, published an acquisition protocol, and reported that everything after
the recording — "decoding, the production measurement, the gate, the correction, the
independent verification and the residual distribution — is automated and already
specified". That last sentence was not supportable: the only acquisition code lived
under the gitignored `work/` tree, and **a clean clone of this repository could not
run any of it**. This phase turns the protocol into tracked, repeatable, verifiable
tooling and tests it end to end.

```text

REAL_GROUND_TRUTH = BLOCKED    still; no real take exists
D3                = NOT ESTABLISHED
D2 / D5           = DEFERRED
production code changed    = NO
production defaults changed = NO
```

### 1.1 Where the code went, and why not `tools/`

`.gitignore` line 32 ignores `tools/` **wholesale** — it holds the vendored
`ffmpeg.exe`, `ffprobe.exe` and the GPAC/NVEncC/QSVEncC distributions, and
`git ls-files tools` returns **nothing**. Tracked acquisition code therefore cannot
live there without `git add -f`, which would contradict the release manifest's tool
whitelist (which expects `tools/ffmpeg.exe` and `tools/ffprobe.exe` and nothing
else). The tooling is tracked under `tests/audio_sync_acquisition/`, alongside the
repository's other tracked test tooling (`tests/selftest/`, `tests/hwdecode/`).

## 2. Protocol audit — the ambiguities, and how each was resolved

The protocol had to be unambiguous before tooling could implement it. Four items
were open; none was resolved by picking a value.

### 2.1 Marker duration: 20 ms vs 0.5 s

The protocol justified a **20 ms** burst in §4 and specified a **0.5 s** one in §5.
The 20 ms detectability experiment cannot be assumed to cover a 0.5 s marker, so
both were measured, along with 100 ms to make the trend visible rather than a
two-point guess.

The first attempt measured the wrong quantity: correlating a 20 ms template against
4 s of unrelated noise finds the noise, and every duration produced 10–80 ms of
apparent localisation error. The quantity the protocol actually needs is a
**difference between two channels of the same file** — "did the delay move between
the start marker and the end marker" — which is a differential measurement on the
same content and is governed by the estimator's resolution, not by absolute
localisation.

| marker | detectability margin over the noise null | differential-offset error (max) | verdict |
|---|---|---|---|
| **20 ms** | **10.29×** | **0.000 samples** | **chosen** |
| 100 ms | 25.00× | 0.000 samples | qualifies |
| 500 ms | 43.85× | 0.000 samples | qualifies |

Every duration recovers the injected offset exactly, so the tie is broken by the
cost: a longer marker occupies more audio and buys detection margin that is already
ample at 10×. **The 20 ms figure is final and the 0.5 s figure in §5 is corrected**
(`work/p4.11-acquisition/marker-design.json`).

### 2.2 The exact time axis

Now generated, not described. `signal.wav` is mono, 48 kHz, 24-bit, 60 s:

```text
sample 12000 .. 12960     marker_start      (20 ms, raised-cosine, 200 Hz-8 kHz)
sample 12960 .. 16680     gap               (80 ms silence)
sample 16680 .. 2856000   measurement body  (band-limited noise, 200 Hz-8 kHz)
                          5 x interior reference events every 10 s, each a
                          marker + 150 ms log sweep, so a delay that moves
                          mid-take is visible between the ends too
sample 2859840 .. 2860800 marker_end
sample 2860800 .. 2880000 tail              (400 ms silence)
```

All boundaries are in `signal-manifest.json` in samples, together with the file's
SHA-256, peak, RMS, clipped-sample count and generator version. `--verify`
re-derives the signal and compares it byte for byte.

### 2.3 Sign convention and calibration offset

Measured against the code, on a ramp where every index can be read by hand
(`work/p4.11-acquisition/sign-chain.json`):

```text
fixture material       tgt[k] = ref[k - d]                 d > 0  =>  tgt LATE
estimate_pair(ref,tgt) returns +d                          (verified 0/1/320/2400/-1/-320/-2400)
sync_fix.shift_stream(delay_samples=s) does out[k] = in[k+s]   (verified both signs, and 0)
so correcting a LATE target by d means shift_stream(delay_samples = +d)
```

For a take, the reported quantities are:

```text
raw_wireless_vs_reference = estimate_pair(reference_channel, wireless_channel)
                            positive  =>  the WIRELESS channel arrives LATE
reference_path_bias       = the session's CABLE_CALIBRATION take, same method
cable_calibrated_offset   = raw_wireless_vs_reference - reference_path_bias
```

**All three are stored**, together with the formula string and the sign direction.
Nothing is subtracted implicitly. A missing calibration is `null`, never `0`, and a
session with **more than one** calibration take is refused outright rather than
having one chosen for it — the bias is a property of the rig, so several calibration
takes give several candidate biases and picking one silently would be an assumption.

The bias is **measured**, so it carries sub-sample error and the derived value
carries it too. On the fixtures: bias `95.9999417` samples, so a +137 take derives
`41.0000583` rather than exactly `41`. That 0.000058-sample error is reported
instead of being rounded into a claim of exactness.

### 2.4 Marker disagreement: kept, marked, and excluded

One outcome, two requirements, both implemented:

```text
raw take                          PERSISTED, never deleted, never rewritten
  -> markers agree  AND traversal constant AND no dropout AND traversal usable
       => CONSTANT_DELAY_CANDIDATE, eligible for a constant-delay residual
  -> markers disagree OR traversal not constant OR dropout
       => TIME_VARYING_CANDIDATE, KEPT, excluded from every constant-delay residual
  -> cannot be determined
       => INSUFFICIENT_DATA
```

A time-varying take is **not** called a corrupt file and is not dropped. Two
mechanisms implement this and they are separate: `preflight.py` classifies on the
marker pair, and `ingest.py` separately requires a constant traversal — because a
take can agree at both markers and still move in between, and the `tv-dropout`
fixture does exactly that.

## 3. The tooling

```text
tests/audio_sync_acquisition/
    generate_signal.py          deterministic signal + manifest
    make_operator_package.py    signal + note templates + checklist, generated together
    preflight.py                what IS this take, before production code runs
    ingest.py                   take it through the real production path
    test_e2e.py                 end-to-end test with negative controls
    acquire_common.py           layout reader, note parser, closed reason vocabulary
    schema.json                 the operator note's required fields
    README.md
```

### 3.1 Signal generation

Deterministic: one seed drives every draw, a second generation is byte-identical,
and `--verify` re-derives and compares. The manifest records the generator version,
the full configuration, the seed, the sample rate and format, the channel count, the
sample count, the duration, the marker layout, the section list, the peak and RMS,
the clipped-sample count and the SHA-256.

Controls: a **different seed must produce a different file** (otherwise the seed
does nothing and reproducibility is meaningless), and a **tampered manifest must
fail `--verify`**. Both fire.

### 3.2 Operator package

Generated in one command so the signal, the manifest, the note templates and the
checklist cannot drift apart. The note template leaves every physical fact blank
with an explicit `___FILL_IN___` marker.

**The physical input mapping is deliberately not pre-filled.** A template that
pre-filled it would invite the operator to accept a wiring nobody checked, and four
mono streams do not say which physical input feeds each of them. An unfilled
template is *refused* by preflight, not silently analysed.

### 3.3 Preflight

Execution status and data status are kept apart, because a take that is unusable is
not a software failure:

```text
execution : PASS / FAIL / BLOCKED / INSUFFICIENT_DATA / NOT RUN
data      : READY_FOR_ANALYSIS / CONSTANT_DELAY_CANDIDATE /
            TIME_VARYING_CANDIDATE / DATA_INELIGIBLE / IDENTITY_UNCONFIRMED
```

Checks: file readable and hashable · container probes · four mono PCM streams ·
48 kHz · 24-bit · stream count and channel layout · note fields present ·
mapping complete and unambiguous · signal SHA matches the manifest · take not
duplicated · duration plausible and consistent with the container · **the declared
marker is actually present in the recording** · clipping · dropout · calibration
take identifiable · `MEASURE` vs `CABLE_CALIBRATION` identity.

Every rejection carries a stable code from a closed vocabulary
(`acquire_common.REASON_CODES`); `"file invalid"` is not a possible output, and the
test asserts that no FAIL has an empty reason list.

### 3.4 Ingest

Reaches the production path through its real API and records every stage
separately, so no stage can stand in for another:

```text
preflight result · truth identity · cable calibration · start/end markers ·
production estimate · evidence gate · plan · apply status ·
independent verification · known-truth residual · truth uncertainty
```

Refusals are **persisted with their input identity**, so a re-run with unchanged
inputs reuses them instead of re-decoding a take already known to be ineligible. The
identity hash covers the take, the note, the signal file and the manifest: a changed
input produces a **new attempt**, byte-identical inputs reuse the existing one.

## 4. Reference calibration

**Mechanics.** The `CABLE_CALIBRATION` take replaces the wireless receiver with a
second direct cable from the same source. Two electrical paths should measure zero;
whatever they measure is the reference-path bias. The measured bias is subtracted
**explicitly**, and the raw value, the bias and the derived value are all stored.

**Signed convention.** `cable_calibrated_offset = raw - bias`, in the same sign as
the raw value: positive means the measured channel's copy arrives LATE. On the
fixtures, a rig bias of +96 samples makes a +96 MEASURE take derive 0 and a +137
MEASURE take derive +41 — both checked, so a silently-passed-through raw value
cannot masquerade as a derivation.

**Truth resolution.** One sample = **20.8 µs**, and that is valid only if the
calibration take's own spread is within one sample, which is reported next to it.
On the fixtures the calibration measured 95.9999417 samples, so the derived value
carries ≈0.00006 samples of the calibration's own error. The tool reports that
error rather than presenting the derived value as exact.

## 5. End-to-end result

`tests/audio_sync_acquisition/test_e2e.py` on 23 fixtures:

```text
VALUE_OK        : 33 / 33
CONTROL_OK      :  9 /  9
FAIL            :  0
CONTROL_FAILED  :  0
```

Positive controls — all with a `MEASURED_ACCURACY`-eligible truth: known zero,
+137, −137, +3600 delays, and a non-zero calibration bias in both a calibration take
and a MEASURE take.

Negative controls, one defect each, each landing in its own state: missing operator
note, wrong signal SHA, mapping that restates stream names, mapping that names only
one stream, mapping with placeholders left in, wrong sample rate, wrong PCM format,
missing marker, corrupt marker, clipped signal, AGC enabled, take too short, unknown
physical identity.

Time-varying controls: start/end markers disagreeing, a delay step inside the take,
and a wireless dropout — all three `TIME_VARYING_CANDIDATE`, and the ingest marks
all three ineligible for a constant-delay residual.

Also verified: no fixture file changed during analysis; no `MEASURED_ACCURACY`
without a calibration take; the bias reported as `null` rather than `0` when absent;
a reused attempt keeps its original `attempt_id`; a changed input produces a new
attempt; a refused take carries no result block.

the production ±80 ms window rather than a new number), and the one-sample
marker/traversal agreement tolerance (the estimator's own integer resolution).

```text

still missing, and only an operator can supply:
  1 x CABLE_CALIBRATION take   (must measure ~0)
  5 x MEASURE at long  TX-RX separation
  5 x MEASURE at medium separation
  5 x MEASURE at short  separation
  plus one filled-in operator note per take, naming which PHYSICAL input
  feeds each of the four streams
```

Once those exist:

```powershell
python tests/audio_sync_acquisition/preflight.py --input takes\
python tests/audio_sync_acquisition/ingest.py --takes takes\
```

`preflight.py` reports per take whether it is usable and what kind of data it is;
`ingest.py` carries the usable ones through the production measurement, gate, plan,
apply, independent verification and the truth-aware residual, and labels each
result according to whether a truth actually exists. No further experiment design
is required.
