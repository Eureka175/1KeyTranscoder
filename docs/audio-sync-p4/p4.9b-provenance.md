## 1. What was reused rather than rewritten

P4.9B adds **no** estimator, **no** ffprobe parser, **no** plan and **no** sync
algorithm. Every measurement comes from production code:

| need | production source | how |
|---|---|---|
| measurement | `core.sync_estimate.estimate_pair` | called directly; geometry read from `core.channel_sync.DEFAULTS` |
| evidence gate | `core.channel_sync.effective_opts(None)` | thresholds **read**, never typed in |
| plan | `core.audio_sync_tv_exec.build_time_varying_plan` | with the production window adapter `aggregate_frames_to_windows` |
| correction | `core.audio_sync_tv_exec.run_time_varying(verify=True)` | the real entry point, real PCM |
| plan geometry | `core.audio_sync_tv.required_window_count` | the production function, not a copied formula |
| channel identity | four sibling mono streams + the production anchor list | never inferred from a file name |

The known-truth material generator is **not** a second framework: the reference
signal and the `src[k] = ref[k - D]` construction are the ones the P4
regression family already uses. What P4.9B adds is band-limited and SNR-controlled
material, which the existing suite does not have, plus a `fixture_sha256` computed
from the **configuration** so a generator change changes the identity.


## 2. The corpora, kept apart

```text
A  20260903 / 20260904 short clips   read during P4.9A; reused here for R2 and R4
B  C1305 / C1306 long clips          the pre-decoded f32 under work/p2/out/raw
C  synthetic known truth             generated by work/p4.9b/fixtures.py
```

Corpus B is the **pre-decoded** PCM that P4.6/P4.7/P4.8 also used
(`work/p2/out/raw/20260919_C13{05,06}_a{1..4}.f32`). Nothing was re-decoded from
the source media for this phase, so a decoding change cannot silently move a
corpus-B number.

**No residual is ever pooled across the three corpora.** The tracked document
reports them in separate sections with separate populations, and §6 of that
document states why a single threshold cannot be derived from them.

```powershell
python work/p4.9b/diag_lag_fix.py
python work/p4.9b/diag_p49a_verifier.py       # does P4.9A's verifier share the defect?

# the tracked document is generated from the artifacts, never hand-edited
python work/p4.9b/assemble_doc.py
```

`assemble_doc.py` reads `work/p4.9b/doc-template.md` and writes the tracked
document. The template is a separate file **on purpose**: the first version filled
the output in place, so a second run destroyed the placeholders and silently
produced empty sections. That is the same input-is-not-an-output mistake P4.9A
recorded for its report generator, and it is recorded here too rather than being
quietly fixed.

## 6. The one defect that changed a published number

The independent verifier's lag axis was folded with `np.argsort` over the
concatenation `[0..n) + [-n..0)`, which puts the negative lags first, so the bin
index did not correspond to the lag for negative lags. Consequence: every POSITIVE
delay was read from the wrong bin. Measured on known shifts: `+46.979` where the
truth was `−320`, and `+13.979` where the truth was `−137`. Negative delays were
unaffected, which is why it presented as a constant `+0.35` sample offset at zero
delay rather than as a broken axis.

P4.9A's verifier was written the same way. Its impact on P4.9A's published results
was checked rather than assumed:

```text
negative-delay pairs   agree exactly between the two implementations
                       (the side every published CH3->CH1 / CH3->CH2 number is on)
near-zero positive     differ by 1.416 samples; P4.9A's CH3->CH4 residuals
                       (0.461 / -0.954) are superseded by R1's exact zeros
```

So P4.9A's `CH3→CH1` / `CH3→CH2` results stand, and its `CH3→CH4` residual figures
are corrected here. The correction is recorded in the tracked document, in P4.9B's
own defect list, and in this file — not applied silently.
