### Signal identity: what the material itself shows

This is the load-bearing measurement of the scan. P4.9A found that exactly **one**
channel pair ever reached the production gate (`CH3→CH4`) and that its offset was
**zero**. A zero is only informative if we know why it is zero, so the inter-channel
structure was measured over all 137 multi-mono clips on a
20 s window:

| stream pair | resolved (Δ) | resolved & zero-lag | corr median | corr max | lag median when resolved | lag range when resolved |
|---|---|---|---|---|---|---|
| `a0→a1` (CH1→CH2) | 0.285 | 0.285 | 0.4683 | 0.993674 | -0.0096 | 0.0068 |
| `a2→a3` (CH3→CH4) | 0.730 | 0.723 | 0.831 | 0.977487 | 0.0609 | 4.5501 |
| `a0→a2`, `a0→a3`, `a1→a2`, `a1→a3` | **0.000** | 0.000 | -0.0002 … 0.0004 | 0.074864 | — | — |

Clustering the streams by the **measured** agreement — never by stream order —
gives `[[0], [1], [2, 3]]`, i.e. two independent sources:

* `stream 0` and `stream 1` are distinct inputs carrying **correlated** material
  (median |corr| 0.4683) — consistent with two microphones on the
  same body hearing the same room;
* `stream 2` and `stream 3` are distinct inputs carrying the **same** off-camera
  signal, agreeing at a median lag of **0.0609 samples**
  with a range of only **4.5501 samples** across
  100 resolved clips;
* the two groups are **mutually uncorrelated** (median |corr| ≤
  0.0004), so they are not two views of one
  signal.

**Consequence, and it is the central result of this section:** the zero that P4.9A
measured on `CH3→CH4` is a property of **how those two inputs are wired** — they
carry the same feed and are internally coincident — and it is therefore **not a
measurement of the wireless link's latency**. This is exactly the trap the phase
brief warned about, and it is now demonstrated from the material rather than
asserted.

```text
source identity confidence:
  that there are two independent sources       HIGH      (measured: |corr| ~ 0 between groups)
  that streams 2 and 3 carry the same feed     HIGH      (measured: corr up to 0.977487, lag ~ 0)
  WHICH physical input feeds each stream       NONE      (not derivable from the files)
  whether streams 0/1 or 2/3 is the wireless one  NONE   (both readings are consistent with the data)
```

### The stereo sources, and why they cannot help

13 single-stream stereo PCM sources exist. They are **ineligible for
the production fixed-delay path by construction** — it gates on the multi-mono
shape (`AudioProbeResult.is_multi_mono`), which a single stereo stream never
satisfies — and none reaches G2 in any case: an L/R delay is a property of one
device's two inputs with no external fact saying what it should be.

They still support a narrower check (below), and it is a real one: it is the first
time in this line of work that the production measurement and an independent
implementation were compared on **real** audio neither had seen.

**Read that table with its population in mind, not as an accuracy result.** On the

There is **no known truth** for an L/R delay, so this is agreement, not accuracy:
it shows the production estimator and an independent full-rate FFT correlation see
the same real signal the same way. It cannot show that either is *right*.

The values themselves are worth one line: C9037 7.0, 阴天手持高晃动低噪点 5.0, 晴天室外手持跟拍几乎无噪点-高晃动-长-多场景亮暗切换2 -4.0, 夜间室内适中偏高噪点-手持变焦 0.0 samples —
i.e. **0 to 7 samples (0–0.15 ms)** of inter-channel delay, which is the order of an
on-body microphone spacing of a few centimetres, not a link latency.

## 5. Acquisition Protocol

The full protocol is in `work/p4.10-source/acquisition-protocol.md` (its content is
reproduced as the tracked record below, so a reviewer does not need the gitignored
tree). Summary of its decisions and why they are what they are:

| decision | value | reason |
|---|---|---|
| recorder | the Sony A7M5 already in use | it is the only device here writing **4 independent mono PCM streams on one clock**, which removes the cross-device timebase problem entirely |
| reference path | **electrical**, direct cable from the same source | an acoustic reference adds an unknown acoustic propagation term on top of the link latency |
| which stream carries what | reference on `stream 0`, wireless on `stream 2` | the two must NOT land on this camera's `stream 2`/`stream 3` pair, which §2 shows are wired coincident — doing so reproduces P4.9A's meaningless zero |
| sample rate / depth | 48 000 Hz, 24-bit | the production path's supported rate; highest linear PCM available |
| channels | 4 × mono PCM | the multi-mono shape is what the fixed-delay path gates on; a stereo stream is ineligible by construction |
| auto-gain / limiter / low-cut / NR | **OFF on every input** | any of them is a time-varying nonlinearity inside the path being measured |
| signal | band-limited noise 200 Hz – 8 kHz + a log sweep, 20 s | matches the estimator's own band. P4.9B measured that material **outside** this band produces **zero** measurable frames, so a mismatched signal would fail for an irrelevant reason |
| take length | 60 s | ≥ 2 production plan windows (30 s) and ≥ 500 measurement frames; a 30 s take leaves a single window, which is what produced zero applied corrections in P4.9A |
| repeats | 5 per configuration, 3 configurations, ≈ 15 min | a stated starting number, **not** a proven statistical requirement — no measurement of within-session link dispersion exists in this project yet |
| markers | full-band burst at both ends of the take | a large link delay must not fall outside the ±80 ms production search window, and a start/end mismatch reveals a delay that MOVED during the take |
| truth | established **by construction**, not discovered | the reference and wireless paths carry the same file from the same player output into the same file on the same clock, so their offset is a pure delay |
| reference-path calibration | **one extra take** with a second direct cable in place of the receiver, which must measure 0 within one sample | this is the step that turns "two paths were recorded" into "the offset between them is meaningful", and its absence is exactly why nothing here is G2/G3 today |

**Expected truth resolution, stated honestly**: the *measurement* resolution is one
sample = **20.8 µs**. The *truth* resolution is one sample **only if** the
cable-to-cable calibration take measures zero to within that; otherwise the truth
resolution is that take's own spread. Which of the two applies must be stated when
the takes are reported.

**What the protocol deliberately does not create**: a calibrated
`uncertainty_samples` (that field does not exist in production, P4.9B §3.1), or a
D3 threshold (a threshold is a product decision about a quantile; the protocol
supplies the distribution, not the decision).

### 5.1 What the operator must produce

```text
takes/<session>/<take_id>.MP4     the recording — not re-encoded, not trimmed
takes/<session>/<take_id>.txt     the operator note
```

The operator note is the part the files cannot carry, and without it the takes are
worthless: `take_id`, timestamp with timezone, camera body serial, **the physical
input mapping for all four streams**, wireless TX/RX model and serial,
transmitter-to-receiver distance, RF channel/band, TX gain and RX output level,
receiver output type, an explicit statement that limiter/AGC/low-cut/NR were off,
the SHA-256 of the played signal file, the signal description, `take_kind`
(`MEASURE` / `CABLE_CALIBRATION` / `MARKER_ONLY`), and free-text notes.

### 5.2 Acceptance and failure

Accepted when: all four streams are mono 24-bit PCM at 48 kHz; the input mapping is
recorded unambiguously; the cable-to-cable take measures 0 within one sample (or its
bias is recorded); ≥ 3 of 5 takes per configuration reach the **shipped** gate
(`usable_frames ≥ 5`, `confidence ≥ 0.3`, `coverage ≥ 0.6` — unchanged); and both
markers in a take agree within one sample.

Failed — as a **data** problem, never as a software failure — when: any input had
AGC, limiter, low-cut or noise reduction on; the signal clipped; the input mapping
is missing; the wireless path dropped out; or the signal's band does not overlap
200 Hz – 8 kHz.
