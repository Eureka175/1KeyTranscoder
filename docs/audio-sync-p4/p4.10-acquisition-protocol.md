# P4.10 — Acquisition Protocol for Real Wireless Ground Truth

> **P4.11 addendum — three ambiguities resolved, and the protocol made executable.**
> Full detail in [`p4.11-acquisition-tooling.md`](p4.11-acquisition-tooling.md); the
> tracked code is `tests/audio_sync_acquisition/`. Nothing below was rewritten
> except the two lines marked *corrected*.
>
> 1. **Marker duration — §4 said 20 ms, §5 said 0.5 s.** Resolved by measurement:
>    the **20 ms marker is final**. Every duration tested (20 / 100 / 500 ms)
>    recovered an injected differential offset to within a sample, and 20 ms carries
>    a **10.3×** margin over the Gaussian noise null while occupying the least
>    audio (`work/p4.11-acquisition/marker-design.json`). §5's 0.5 s figure was
>    wrong and is corrected there.
> 2. **Exact time axis — now generated, not described.** Run
>    `python tests/audio_sync_acquisition/generate_signal.py`: it writes `signal.wav`
>    (mono / 48 kHz / 24-bit / 60 s) plus `signal-manifest.json` with every section
>    boundary in samples and the file's SHA-256. It is deterministic — `--verify`
>    re-derives and compares byte for byte.
> 3. **Sign convention and calibration arithmetic — measured, not assumed.** Proved
>    on a ramp (`work/p4.11-acquisition/sign-chain.json`) and implemented in
>    `ingest.py`: `estimate_pair(reference, wireless)` returns `+D` when the
>    **wireless** copy is **late**; `shift_stream(delay_samples=+D)` does
>    `out[k] = in[k+D]`; and
>    `cable_calibrated_offset = raw_wireless_vs_reference - reference_path_bias`
>    with all three values stored and **never** subtracted silently.
> 4. **Marker disagreement — one outcome, two requirements.** A take whose markers
>    disagree is **kept**, marked `TIME_VARYING_CANDIDATE`, and excluded from every
>    constant-delay residual. It is never deleted and never called a corrupt file.

**Status**: this protocol has **not** been executed. It exists because the scan in
this phase found no source on this machine that carries an independent delay truth
(`work/p4.10-source/truth-anchor-audit.json`). It is written to be executable with
equipment already present, and every parameter is given with its reason rather than
presented as a proven statistical threshold.

## 0. What the scan established, and why that shapes the design

| finding | evidence | consequence for the protocol |
|---|---|---|
| every multi-channel source is a Sony body recording **4 mono PCM streams** at 48 kHz | `work/p4.10-source/inventory.json`, 148 containers | the reference and the wireless signal can be recorded **into the same file on the same clock** — no cross-device timebase problem |
| the 4 streams form **two independent sources**: {stream 0, stream 1} and {stream 2, stream 3} | `work/p4.10-source/channel-forensics.json`: cross-pair correlation median ≈ 0.000, within-pair 0.47 and 0.83 | the camera already records an on-body pair and an off-camera pair; the protocol only has to make the **identity** of each pair known |
| the off-camera pair (`stream 2`, `stream 3`) agrees with itself at **0.06 sample median lag**, range 4.6 samples over 137 clips | same file, 73 % of clips resolved | that near-zero is a property of how those two inputs are wired, **not** a measured link delay; the protocol must therefore separate the two paths onto **different** streams, never place reference and wireless on the pair that already tracks itself |
| no source carries any external reference | `truth-anchor-audit.json`: 1 candidate anchor proposed (a file whose name means "delay"), **rejected** — it has no audio stream at all | a truth must be *created*, by construction, not discovered |

## 1. Equipment (all already present)

| item | role | why this and not something else |
|---|---|---|
| Sony A7M5 body + lens | the recorder | it is the only device here that writes **4 independent mono PCM streams, one per input, on one clock**. One file, one clock, four physically distinct inputs — the entire protocol depends on this and nothing else needs to be bought |
| XLR / 3.5 mm inputs as the body provides | reference path and wireless receiver output | the four inputs must be routed to four *known* physical inputs, not left on AUTO |
| the wireless system under test (transmitter + receiver) | the device being measured | it is the thing whose latency is in question |
| a cable from the signal source to the camera, and the same source into the transmitter | the two paths | the reference must be **electrical**, not acoustic (see §4) |
| a signal source that can play a deterministic file | test signal | a repeatable file is what makes the take re-derivable |

**Not required, and deliberately not used**: an external audio interface (it would
introduce a second clock), a second camera (same reason), or any new software.

## 2. Wiring

```text
                       ┌──────────────────────────────┐
   test signal file ──▶│  player (phone / PC / field   │
   (deterministic)     │  recorder line-out)           │
                       └───────┬───────────────┬───────┘
                               │               │
                    ┌──────────▼───┐      ┌────▼──────────┐
                    │ DIRECT CABLE │      │  WIRELESS TX  │
                    │  (electrical)│      └────┬──────────┘
                    └──────┬───────┘           │  radio
                           │             ┌─────▼─────────┐
                           │             │  WIRELESS RX  │
                           │             └─────┬─────────┘
                           │                   │ (electrical output)
   ┌───────────────────────▼───────────────────▼───────────────────────┐
   │                     Sony A7M5  —  ONE file, ONE clock              │
   │   stream 0  CH1  = REFERENCE  (direct cable)                      │
   │   stream 1  CH2  = spare / second reference or room mic           │
   │   stream 2  CH3  = WIRELESS A  (receiver output)                  │
   │   stream 3  CH4  = WIRELESS B  (second receiver output, if any)   │
   └───────────────────────────────────────────────────────────────────┘
```

**The assignment must be written down at the time of recording** and must match
what actually happened. Stream order is the production `audio_position`
convention; it is not evidence about which physical input a stream carries, so the
mapping is recorded as an operator note (see §8) and not inferred later.

Do **not** put the reference and the wireless output on streams that this machine's
existing material shows to be wired together (the current camera's `stream 2` /
`stream 3` pair). If both paths land on that pair, the measurement collapses to the
same near-zero that P4.9A found, and it will mean nothing again.

## 3. Recording format

| setting | value | reason |
|---|---|---|
| sample rate | **48 000 Hz** | the production path's `supported_sample_rates`, and the rate of every existing source |
| bit depth | **24-bit** | highest linear PCM the body offers; quantisation noise then sits far below any delay-relevant effect |
| channels | **4 × mono PCM** | the multi-mono shape is what the production fixed-delay path gates on (`AudioProbeResult.is_multi_mono`); a stereo stream is **ineligible by construction** |
| container / codec | body's XAVC with linear PCM (`pcm_s24be` / `ipcm`) | the same shape as the existing corpus, so the same decode path applies |
| level | peaks between **−12 and −6 dBFS** | loud enough to clear `frame_min_rms_dbfs` on every frame, short of clipping; a clipped reference is a distorted reference |
| duration | **60 s per take** | see §6 |
| auto-gain / limiter / noise reduction | **OFF on all four inputs** | any of these is a time-varying nonlinearity in the very path being measured |

## 4. Test signal

One file, deterministic, repeated identically in every take.

| property | recommendation | reason |
|---|---|---|
| content | **band-limited noise, 200 Hz – 8 kHz**, plus a **log sweep** | the production estimator decimates to 8 kHz and its fine stage bands 200 Hz – 8 kHz; a signal inside that band is what the estimator is built for. P4.9B measured that **outside** it the estimator refuses frames entirely (narrow bands → broad correlation peak → every frame fails the estimator's own success test) |
| duration | 20 s continuous, then 5 s silence, then repeat | long enough for ≥ 100 measurement frames at the production 200 ms/100 ms geometry; the silence gives an unambiguous energy boundary |
| level | constant, no fades | a fade is a time-varying amplitude and adds nothing |
| **not** a click or clap | | a single transient gives one observation with an onset uncertainty of milliseconds; broadband continuous material gives hundreds of independent frames |
| peak-to-average | moderate | a very high crest factor wastes headroom |

**Why a 20 ms burst is a usable reference event, measured rather than assumed.**
The marker's job is to be *findable* by correlation, so the question is whether a
correlation peak at the level a real marker produces could also arise from noise.
`work/p4.10-source/marker_detectability.py` measures the null: a 20 ms wideband
burst of the same envelope correlated against **independent Gaussian noise** of the
same length, over 5 000 trials, gives a normalised peak with

```text
median 0.0216     p99 0.0814     max 0.1453
```

Nowhere near 0.2, by a factor of 6.8 at the extreme. A real marker is therefore
separable from noise: its normalised peak sits close to a perfect self-correlation
(1.0) while noise alone never leaves the low hundredths. That is what makes the
marker usable — and it is why the marker is a short **wideband** burst rather than
a tone, since a tone's correlation peak is periodic and would be ambiguous inside
the search window.

A second, independent instance of the same argument: P3.10's own residual artifacts
report a **peak-over-noise of 9.4 to 22.2** on real long-form material
(`work/p3/p310/residual/20260919_C1305/ch3_to_ch4_w5_h10.json`). Two different
quantities, same conclusion — the detector's output on real material is far outside
what noise produces.

**Why bandwidth is the crux and not an afterthought**: P4.9B measured that a
20 s take of narrow-band material produced **zero** measurable frames while the
same take wide-band produced ~200, all at the same delay. A test signal whose
bandwidth does not match the estimator's band would make the experiment fail for a
reason that has nothing to do with the wireless link.

## 5. Reference events

| event | how | what it is for |
|---|---|---|
| **start marker** | a 20 ms wideband burst immediately before the noise, on **both** paths *(duration corrected by P4.11 on measurement; this line said 0.5 s)* | gives a coarse alignment good to well under one frame, so a large link delay cannot fall outside the ±80 ms production search window |
| **end marker** | the same 20 ms burst after the noise ends *(corrected as above)* | detects a delay **change** across the take; if start and end markers give different answers, the link moved during the recording and the take is a time-varying measurement, not a constant-delay one |
| **take boundary** | hand clap, then 3 s of silence, before the next take | lets takes be cut apart unambiguously without relying on file names |

## 6. Duration and repeats — with the reason, not as a proven threshold

| parameter | value | reason |
|---|---|---|
| take length | **60 s** | 30 s is the production plan window. A take shorter than 30 s leaves the time-varying plan with a single window and P4.9A already showed what that produces: 137 clips, one eligible channel pair, **zero** corrections applied. 60 s gives ≥ 2 plan windows and ≥ 500 measurement frames |
| takes per configuration | **5** | enough to see whether the link's delay is reproducible within a session. **This is a starting number, not a demonstrated statistical requirement** — nothing in this project has measured the within-session dispersion of a wireless link, so no defensible larger number can be quoted. If the 5 takes disagree by more than the estimator's own integer resolution, the repeat count is the first thing to raise |
| configurations | **3** | the smallest set that can distinguish "the link has latency L" from "the link has latency L at this distance": short / medium / long transmitter-to-receiver separation |
| total | **15 takes, ≈ 15 min of recording** | sized to be finishable in one session with one operator |

## 7. Ground truth: how it is established

The truth is established **by construction**, and it is a truth about *one*
quantity only:

```text
WHAT IS KNOWN
  the reference path and the wireless path carry the SAME signal file,
  started from the same player output, recorded into the SAME file on the
  SAME clock. Therefore the sample offset between them is a pure delay:
  no clock drift term, no cross-device timebase term.

WHAT IS MEASURED
  the sample offset D between the reference stream and the wireless stream.

WHAT IS ONLY INFERRED
  that D is attributable to the wireless link. D is the sum of the radio
  latency AND the electrical delay of the receiver's output stage AND any
  gain/limiter group delay that was NOT switched off. The protocol therefore
  fixes those by construction (limiter off, fixed level) rather than by
  assumption, and the residual analogue path delay is reported as part of D
  and never subtracted on a guess.

WHAT THIS IS NOT
  D is NOT the "absolute latency of the wireless system" in a datasheet
  sense. It is the end-to-end delay of this transmitter, this receiver, these
  cables and these levels, measured on this clock. That is exactly the
  quantity the production path would have to correct, which is why it is the
  right one to measure.
```

### 7.1 Reference-path calibration

Required, and cheap: record **one extra take** with the wireless receiver replaced
by a second direct cable (i.e. reference on stream 0, a second cable from the same
source on stream 2). Two identical electrical paths should measure **0 ± the
estimator's own resolution**.

```text
if the cable-to-cable take measures 0   -> the reference path contributes no
                                           offset and D is attributable to the link
if it measures non-zero                 -> that value is the reference-path bias and
                                           MUST be recorded and reported, not
                                           subtracted silently
```

This is the step that turns "two paths were recorded" into "the offset between them
is meaningful", and it is the step whose absence is why nothing on this machine
qualifies as G2/G3 today.

### 7.2 Expected truth resolution

| source of uncertainty | magnitude | how it is bounded |
|---|---|---|
| sample quantisation | 1 sample = **20.8 µs** | arithmetic |
| the estimator's own integer resolution | 1 sample at 48 kHz | P4.9B R3: max |error| ≤ 1 sample over 10 233 frames on clean band-limited material |
| independent verifier sub-sample agreement | ≤ 0.5 sample | P4.9B: two implementations agree to 0.0002 samples on known truth |
| **reference-path analogue delay** | not known a priori | bounded by the cable-to-cable calibration take (§7.1) |
| radio-side variation within a take | unknown until measured | bounded by the start/end marker comparison (§5) |

**Honest statement of the expected resolution**: the *measurement* resolution is
one sample (20.8 µs). The *truth* resolution is one sample **only if** the
cable-to-cable calibration take measures zero to within that; otherwise the truth
resolution is the calibration take's own spread. The report of the acquisition must
state which of the two applies.

## 9. Acceptance criteria, and failure conditions

The acquisition is **accepted** when:

1. every take has all four streams as mono 24-bit PCM at 48 kHz;
2. the operator note states the physical input mapping unambiguously;
3. the **cable-to-cable calibration take measures 0 within one sample** (or its
   measured bias is recorded);
4. at least 3 of 5 takes in each configuration reach the production evidence gate
   (`usable_frames ≥ 5`, `confidence ≥ 0.3`, `coverage ≥ 0.6` — the shipped gate,
   unchanged);
5. the start and end markers in a take agree to within one sample (a take that
   fails this is a **time-varying** measurement and is reported as such, not
   discarded).

The acquisition **fails** — and this must be reported as a data problem, not a
software failure — when:

* any input had AGC, a limiter, a low-cut filter or noise reduction enabled;
* the signal clipped on any stream;
* the operator note does not state the input mapping;
* the wireless path dropped out (the take can still be kept, but it cannot
  contribute to a constant-delay accuracy figure);
* the signal's band does not overlap 200 Hz – 8 kHz.

## 10. What can then be computed, and what still cannot

**Can be computed** — all three of the things that are missing today:

| quantity | from which takes |
|---|---|
| real-material **estimator accuracy** against a known sample delay | any MEASURE take, reference stream vs wireless stream |
| the **post-correction residual** on real material | the production chain applied to the same take |
| a **residual distribution** over a real population | 15 takes × several configurations |

**Still cannot be computed** from one session:

* any statement about a **different** wireless system, band, or body;
* a **calibrated `uncertainty_samples`** — that figure does not exist in production
  (P4.9B §3.1), and this protocol does not create it;
* a **D3 acceptance threshold**, because a threshold is a product decision about
  which quantile of the residual distribution is acceptable. The protocol supplies
  the distribution; it cannot supply the decision.

## Annex — the two reference designs this protocol is based on

Both were consulted for experimental design only; neither substitutes for this
project's own measurement evidence.

* **Rational Acoustics — measuring a wireless unit for linear time invariance.**
  The relevant idea is that a wireless link must be *tested for time invariance*
  before a constant-delay correction can be justified, which is exactly why §5 puts
  a marker at both ends of the take.
  <https://support.rationalacoustics.com/support/solutions/articles/150000194022-how-to-measure-your-wireless-unit-for-linear-time-invariance>
* **gavv/signal-estimator** — loopback and input-sync latency measurement.
  The relevant idea is the direct electrical loopback as the reference path, which
  is why §7.1 insists on a cable-to-cable calibration take.
  <https://github.com/gavv/signal-estimator>
