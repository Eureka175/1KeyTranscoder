# v0.8.1 部署说明 — Gyroflow 元数据修复版

针对 v0.8.0 交付的 Sony `.MP4` 在 Gyroflow 中读不到陀螺仪数据的问题。
根因取证见 `metadata_forensics/sony/v0.8.0_gyroflow_root_cause.md`。

---

## 1. 这个包修了什么

**唯一的功能性修复**: `place_final` 在把 MOV 中间产物转成 MP4 时,用
`MP4Box -new -add` 逐轨重建容器,**文件级 `meta`(Sony nrtm)盒会被丢掉**;
Gyroflow 的 Sony 解析器必须先看到它才肯解析 rtmd 轨,于是同一份逐字节
完好的 rtmd 载荷被读出 **0** 个 IMU 样本。

现在重封装之后会:

1. 从 bundle manifest 记录的源文件把 nrtm meta(XML + Lens profile 条目)
   重新应用到交付物;
2. 补回 `tref/cdsc`(rtmd → video,重封装同样会丢);
3. **断言**两者都在,缺失就报错并把半成品删掉 —— 而不是静默交付。

同时堵掉三处"静默"(这是它当初能跑完 709 个文件的原因):

- `checker.py`:`advanced` 档未装 Gyroflow 时不再无声跳过,而是记录
  `gyroflow.status = SKIPPED` 并打印 WARNING;`basic` 档也会记录
  "消费端未校验"这一事实。
- `validate.py`:`nrtm.meta` 的**存在性**检查从 `advanced only` 提到**所有档位**
  (它是廉价且决定性的判据;原先连 `basic` 都不查)。
- `tests/selftest`:`l2_file_level_meta` 回归用例钉住重封装丢失与恢复,
  并含"故障前提"断言,防止用例退化成永真。

## 3. 重跑后怎么确认修好了

**看每个文件的日志**(`logs/files/<date>/<name>_HQ.log`),容器重封装那三行:

```
CONTAINER | container-only re-mux: output.mov (6 track(s), movie timescale 60000)
            -> container-remux.MP4 [stream copy, no re-encode]
CONTAINER | container re-mux: file-level meta (nrtm) re-applied from the pre-remux artefact
CONTAINER | file-level meta preserved (hdlr='nrtm', xml preserved, lens item 7903 B sha256=...)
CONTAINER | tref/cdsc re-applied (6->1)
CONTAINER | tref/cdsc preserved
```

`file-level meta preserved` 出现在**每个 Sony MP4 源**的交付日志里 = 生效。

**看 PRESERVATION_REPORT 那一行**:

```json
"gyroflow": {"status": "SKIPPED", "detail": "Gyroflow not installed ..."}
```

v0.8.0 这里写的是 `"gyroflow": null` —— 现在至少能一眼看出"这轮没做消费端校验"。

**抽样实测**(推荐): 把 `testsets/v0.8.0_failed/20260901_C0955.MP4` 对应的新产物
丢进 Gyroflow GUI,应当能识别 `Sony ILCE-7M5` 并读出运动数据。
命令行等价做法:

```powershell
& "D:\Gyroflow-windows64\Gyroflow.exe" "<新产物>.MP4" `
    --export-metadata "2:F:\gf_check.json"
# 期望 raw_imu 非空 (本例参考值 14014)、detected_source = "Sony ILCE-7M5"
```

## 4. 部署到远端机器

1. 把 zip 拷到远端,解压到新目录(不要覆盖旧的 0.8.0,留着做对照)。
2. **远端没有装 Gyroflow** —— 这正是缺陷能静默通过的一半原因。
   建议这次装上(`D:\Gyroflow-windows64` 或 `C:\Program Files\Gyroflow`),
   或用 `--gyroflow <path>` 指过去,并**用 `--check advanced` 或 `full` 跑**;
   否则消费端校验仍然不会发生(现在至少会有 WARNING 和 SKIPPED 记录)。
3. 沿用原来的输出根目录即可;中间产物目录结构没变。

## 5. 存量修复(重要,可能省掉大量重跑)

**已交付的坏文件不必重跑 x265。** `stage.mov` / `output.mov` 这两个中间产物
是**完好的**(Gyroflow 能读,14014 IMU);坏的只是最后一步重封装的结果。

如果远端 `.1ktwork/<job>/final/output.mov` 还在:

- 方案 A(推荐): 用新版对同一批源**重跑**,`place_final` 会重新生成正确交付物;
  但 x265 会重编一遍。
- 方案 B(省时): 写个一次性脚本,对每个 `output.mov` 只做"重封装 + 补 meta + 补 tref"
  (即新版 `place_final` 的行为),不碰视频编码。`gpac.restore_file_level_meta()`
  与 `gpac.restore_track_refs()` 已可直接调用。

**但 `.1ktwork` 默认会被 GC 清掉**(`cleanup_work_dir`),所以大概率只剩方案 A。

### 本轮发现并修掉的一个自伤回归

值得记一笔:第一版 Fix B 把"未跑消费端校验"记成 `status = "SKIPPED"`,
而 `1kt.py:854` / `core/batch_hw.py:1077` 原本是
`if gyro.get("status") != "PASS": return "failed"` —— 于是**每个 Sony 文件在
`--check basic`(即你实际使用的档位)下都会失败**。L3 的 `C1_sony_nvenc_basic: rc=1`
把它抓了出来。两处门控已改为只对真正的 `FAIL` 阻断交付;`SKIPPED` 只记录、不阻断。
若没有跑那轮 L3,这个回归会被直接打包发出去。
