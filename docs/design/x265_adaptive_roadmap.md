# x265 自适应路线：可行性分析与计划书

日期：2026-11-05
范围：x265 软件编码路径（纯 CPU / 4K 4:2:2 10-bit 场景优先）
状态：计划书，未实施；所有自适应功能默认关闭，显式开启，决策可审计。

## 0. 总体判断

| Part | 目标 | 可行性 | 主要代价 | 优先级 |
|---|---|---|---|---|
| P0 目标体积/码率闭环 | 按目标大小/码率决定 CRF/2-pass | **高**（技术） / **中**（4K 时间成本） | 两遍编码时间、统计文件、质量语义变化 | **最高** |
| P1 实际复杂度自适应 | 用样片实际 bit 需求替代纯 OB 分类 | **中** | 需要样片分析和校准；不会一次到位 | 高 |
| P2 静态画质保护 | 静态场景不被 AQ/cutree 过度压码率 | **中** | 场景检测 + x265 zones，验证成本高 | 中 |
| P3 分段/场景级 QP | 按场景复杂度分配 CRF/QP | **中低** | 依赖 P1/P2，zones 与 2-pass 交互复杂 | 最后 |
| P4 输出规格自适应 | 4:2:2→4:2:0、降分辨率 | **高**（技术） / 需产品决策 | 改变交付规格，不可默认 | 可与 P1 并行 |

一句话：

> 先做 **P0 结果闭环**，再做 **P1 内容理解**；P2/P3 是精细质量保护，P4 是显式规格降级。
> 不要在 P0 之前继续堆静态参数。

---

## 1. 共同架构

不把自适应逻辑塞进 `encoders/x265.py`。新增一个**决策层**：

```text
prepare_source()
  -> core.adaptive.plan_x265(...) -> EncodePlan
  -> x265 build_command(plan)
```

建议新增：

- `core/adaptive.py`
  - `EncodePlan`
  - `TargetSizePolicy`
  - `ComplexitySample`
  - `ZonePlan`
- `x265_scaling.json` 新增可选段：

```json
"adaptive": {
  "enabled": false,
  "mode": "off | target_size | target_bitrate | sample_crf",
  "sample_seconds": 20,
  "target_size_ratio": null,
  "crf_min": 18,
  "crf_max": 32,
  "size_tolerance": 0.05,
  "allow_two_pass": true
}
```

原则：

1. base `x265.json` 仍是权威基线；自适应只产生**本次文件的计划**；
2. 每次决策写入日志和 report：`adaptive.mode / chosen_crf / target / predicted / actual / fallback`；
3. 任何失败或越界回退到 base profile；
4. 自适应模式不承诺 bit-exact，默认模式仍保持现有行为；
5. 样片/统计文件放在 `.1ktwork/<job>/adaptive/`，不落 C 盘。

## 2. P0：目标体积 / 码率闭环

### 2.1 目标

用户给出目标大小或目标码率，系统自动选 CRF/2-pass，不再手动试 CRF。

### 2.2 方案对比

| 方案 | 精度 | 时间成本 | 质量稳定性 | 推荐 |
|---|---|---|---|---|
| A. 两遍 ABR 目标码率 | 高 | +30–60% | 中（ABR 与 CRF 语义不同） | **主方案** |
| B. 样片 CRF 搜索 | 中 | +1 次样片/候选 | 高（仍是 CRF） | 短素材/补充 |
| C. CRF + 监测首段码率 | 低 | 低 | 差（不能中途改 CRF） | 不推荐 |

对 4K50 10-bit 4:2:2、slow preset：

- 两遍编码总时间约为单遍的 **1.3–1.6×**；
- 样片 CRF 搜索若同 preset 编 20 s，样片本身约 20–40 分钟/候选，不现实；
- 因此主方案选 **两遍 ABR**，样片搜索只用于短片段或快 preset 预判。

### 2.3 算法

1. 由目标大小算目标总码率：

```text
target_total_bps = target_bytes * 8 / duration
video_bps = target_total_bps - audio_bps - subtitle_bps
```

2. 第一遍：
   - `x265-params pass=1:stats=<work>/x265_2pass.log`
   - 可用较快的 `slow-firstpass` 策略（需实测确认）；
   - 不输出成品。
3. 第二遍：
   - `-b:v <video_bps>` + `pass=2:stats=...`
   - 保留 `vbv-maxrate/vbv-bufsize` 和 `const-vbv`；
   - `cutree`/AQ 仍按 profile，不动设计意图。
4. 输出报告预测/实际大小；超过 tolerance 时标记 `size_miss`，但不自动重编（除非显式允许重试）。

### 2.4 改动点

- `core/adaptive.py`：目标计算、计划生成；
- `1kt.py`：在 `prepare_source` 后、`encode_one` 前调用；
- `encoders/x265.py`：支持 `pass=1/2`、`-b:v`、stats 路径；
- `core/config.py`：校验 adaptive 段；
- report/dashboard：新增 adaptive 字段；
- 失败回退：无法两遍时回退 base CRF。

### 2.5 验收

- 同一素材，目标大小误差 **≤5%**（正常内容）；
- 样片/整片质量不低于同大小手工 CRF 的合理范围；
- 默认关闭时行为与当前逐位一致；
- `.1ktwork` 内统计文件清理正确；
- 中断/续跑行为明确（P0 先只支持完整两遍，不做中途续跑）。

### 2.6 可行性与风险

**可行性高，但 4K CPU 时间成本高。**
风险：

- ABR 在高复杂度 4K 上的质量可能不如 CRF；
- 两遍会让 8 小时任务变成 11–13 小时；
- 目标大小极端小（如 <15% 源）时需要配合 P4（降规格），不能只靠 x265。

**建议：P0 默认关闭，先支持 `--target-size` / `--target-bitrate` 显式开启。**

## 3. P1：实际复杂度自适应

### 3.1 目标

不再只用容器 OB 分类，而是用**样片实际编码结果**判断内容复杂度，调整 CRF/VBV/AQ。

### 3.2 可采集特征

优先级从低成本到高成本：

1. 第一遍 stats（若 P0 开启）：
   - 每帧/每场景的 bits、QP、运动向量统计；
2. 样片快速编码（fast preset，低分辨率可选）：
   - bits/frame @ 固定 CRF；
3. ffmpeg 轻量分析：
   - `freezedetect`（静态段）；
   - `signalstats`（亮度/噪声）；
   - 场景切换分数。

### 3.3 自适应动作

- CRF 偏移：`base_crf + delta`，范围 ±0.5–2；
- VBV target_ratio 乘数：0.85–1.15；
- `aq-strength`/`psy-rd` 小范围调整；
- **cutree 不自动改变**：HQ/UHQ 继续关闭，SMALL/FAST 继续开启。

所有动作必须有上下限和审计记录。

### 3.4 改动点

- `core/adaptive.py`：`ComplexitySample` + 校准表；
- `x265_scaling.json`：`complexity_adaptation` 段；
- 缓存：按源 sha256 + 几何 + preset 缓存样片结果，放在 `.1ktwork`；
- report：记录特征、偏移、最终参数。

### 3.5 验收

- 与 P0 解耦：P1 关闭时 P0 仍可用；
- 至少在 C1305/C1306、4K50 样例上做 A/B；
- 静态段质量不下降；体积改善方向正确；
- 样片缓存命中时额外耗时可控。

### 3.6 可行性与风险

**可行性中。**
最大风险是**校准**：样片 bit 需求与整片的相关性不稳定，尤其长镜头、渐变、颗粒内容。
建议先只做**保守的小偏移**，不做大范围自动 CRF 重估。

## 4. P2：静态画质保护

### 4.1 目标

在不打开 HQ/UHQ `cutree` 的前提下，避免静态/渐变区域被 CRF/VBV 压坏。

### 4.2 方案

1. 场景/静态检测：
   - ffmpeg `freezedetect` 或场景分数；
   - 输出帧区间。
2. 将静态区间映射为 x265 zones：
   - 静态区间使用更低 CRF（或保持基础 CRF）；
   - 运动区间维持基础 CRF；
   - zone 数量设上限（如 32），避免命令过长。
3. 仅对 HQ/UHQ 启用；SMALL 继续用 cutree 的体积策略。

### 4.3 风险

- zones 与两遍 ABR 的交互复杂；
- 静态检测误判会把普通场景当静态；
- QP/CRF zone 边界可能造成可见跳变；
- 需要帧精确映射（源 fps/timeline）；
- 质量验证成本高。

### 4.4 验收

- 静态段 SSIM/PSNR 不差于基线；
- 总大小增幅受控（例如 ≤3%）；
- zone 边界无明显跳变；
- 失败或检测不确定时自动回退无 zones。

### 4.5 可行性与风险

**可行性中，优先级低于 P0/P1。**
建议等 P0/P1 稳定后再做，否则同时引入两套变量很难归因。

---

## 5. P3：分段/场景级 QP

### 5.1 目标

按场景复杂度在整片范围内分配 CRF/QP，进一步优化体积-质量曲线。

### 5.2 依赖

- P1 的场景/复杂度特征；
- P2 的 zones 生成与验证；
- P0 的目标大小/码率框架。

### 5.3 方案

- 场景切分（ffmpeg scene score / 第一遍 stats）；
- 每个场景分配 `crf` 或 `qp`；
- x265 `zones=start,end,crf`；
- 总码率/大小由 P0 目标约束；
- 限制 zone 数量、最小场景长度，避免碎片化。

### 5.4 可行性与风险

**可行性中低。**
复杂度最高：

- 场景检测稳定性；
- zones + 2-pass 兼容性；
- 边界帧质量；
- 调试/验收成本大。

建议放到最后，且先只做“高复杂度场景 + 静态场景”两类粗粒度 zone，不做逐场景最优。

---

## 6. P4：输出规格自适应

### 6.1 目标

当体积优先且允许改变交付规格时：

- 4:2:2 → 4:2:0；
- 4K → 1440p/1080p；
- 不改变帧率，避免时间轴问题。

### 6.2 方案

- 新增显式开关：
  - `--output-chroma 420|422`
  - `--output-resolution 2160p|1440p|1080p`
- 在 ffmpeg 命令中插入 `scale/format` 滤镜；
- 更新输出 probe/报告；
- 对 Sony/DJI 保留管线：只影响视频编码中间体，元数据仍按原 timeline 重建；
- 默认保持源规格。

### 6.3 验收

- 输出规格正确；
- 音频/元数据/timeline 不受影响；
- 体积收益明确；
- 规格变化在日志/report 中可见；
- 4:2:0/降分辨率不默认。

### 6.4 可行性与风险

**技术可行性高，主要是产品策略风险。**
优点：对体积的收益远大于任何 x265 参数微调；
缺点：改变交付规格，不可静默，不可作为默认。

## 7. 推荐实施顺序与工作量

| 顺序 | Part | 预估工作量 | 依赖 | 建议 |
|---|---|---:|---|---|
| 1 | P0 目标体积/码率闭环 | 3–5 天 | 无 | 先做两遍 ABR + 报告 |
| 2 | P1 实际复杂度 | 4–6 天 | P0 的 stats 可复用 | 先保守偏移，后校准 |
| 3 | P4 输出规格（显式） | 2–4 天 | 无 | 可与 P1 并行 |
| 4 | P2 静态保护 | 5–7 天 | P0/P1 | zones + 静态检测 |
| 5 | P3 分段 QP | 5–8 天 | P1/P2 | 最后，只做粗粒度 |

总计约 **19–30 工程日**，不含 4K 实编的机器时间与语料校准。

## 9. 结论

- **P0 最值得先做**：它直接解决“CRF 撞 VBV、大小不可控”的问题；
- **P1 是 P0 的增强**，不要在没有目标闭环时单独做复杂内容分析；
- **P2/P3 是质量保护**，等 P0/P1 稳定后再上；
- **P4 是体积收益最大的显式规格手段**，但必须作为产品决策，默认关闭；
- 任何自适应都不能静默改变输出语义，尤其是音频对齐、元数据和容器 timeline。
