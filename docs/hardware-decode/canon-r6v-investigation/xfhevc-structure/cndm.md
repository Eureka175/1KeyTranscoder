# cndm 轨（Canon 定时 metadata）结构专项

**对象**：XF-HEVC 的 `cndm` 轨（handler `meta`，`tref cdsc` → 视频轨）
**方法**：ISOBMFF 直读 + KLV 框架解析，**只读**
**机读产物**：`cndm-structure.json`

> 素材：A0013C699（154 样本）、A0013C700（686 样本）
> 两者 `cndm` 结构完全同构（同机同固件）。

---

## 1. 结论摘要

| 项 | 结论 |
|---|---|
| 采样入口 | `cndm`（payload 仅 8 B：`00000000 00000001`） |
| **样本大小** | **1064 B 定长**，全部样本一致 |
| 总载荷 | A699: 154 × 1064 = **163,856 B**；A700: 686 × 1064 = 729,904 B |
| `tref` | `cdsc` → track_id 1（视频轨） |
| `stts` | delta 恒 1001（与视频同拍，逐帧一条） |
| 块偏移 | `co64`，11 chunk（与视频轨同数量） |
| 编码框架 | **Canon 私有头（28 B）+ KLV Local Set 序列** |
| **每帧变化量** | **177 / 1064 字节（16.6%）**，且**只落在 Local Set[3] 内** |
| 内部字段语义 | ❌ **未解出**（见 §4） |

## 2. 载荷布局（已核对）

```
偏移      内容
─────────────────────────────────────────────────────────
[0, 28)   Canon 私有头（非 KLV）
[28, …)   KLV Local Set 序列，每个 = 16B SMPTE UL + BER 长度 + 值
```

### 2.1 Canon 私有头（28 B）

```
01000000 0c000000 0001b50b 67d00300 00000000 02000000 0c040000
```

| 偏移 | 读数（大端） | 观察 |
|---|---|---|
| 0–3 | 16777216 (`0x01000000`) | 常量 |
| 4–7 | 201326592 (`0x0C000000`) | 常量 |
| 8–11 | `0x0001B50B` | 常量 |
| 12–13 | u16 帧计数 | **逐样本 +1，但非剪辑内帧号**（见下） |
| 14–15 | `0x0300` | 常量 |
| 16–19 | 0 | 常量 |
| 20–23 | `0x02000000` | 常量 |
| 24–27 | `0x0C040000` | 常量 |

**偏移 12 不是剪辑内帧号**：A0013C699 首样本 = **26576**，
A0013C700 首样本 = **465**。两者差值 26111 ≈ 26112 = 17 × 1536。
推测是相机侧持续递增的计数器（与录制/写卡位置相关），
**不能当作帧索引使用**。

### 2.2 KLV Local Set 序列（A699 首样本共 6 个）

| # | 偏移 | 长度 | 长度字段 | UL（后缀） | 值 sha256(8) |
|---|---|---|---|---|---|
| 0 | 28 | 24 | 4 B (`83 00 00 18`) | `…0c02010101010000` | `e93ae29d` |
| 1 | 72 | 163 | 4 B (`83 00 00 a3`) | `…0c02010102010000` | `5b61f5ec` |
| 2 | 255 | 214 | 4 B | `…0c0201017f010000` | `3287484e` |
| 3 | 489 | **475** | 4 B | `…0c0201017f010000` | `a275f073` |
| 4 | 984 | 20 | 4 B | `…0c0201017f010000` | `23fe1172` |
| 5 | 1024 | 20 | 4 B | `…0c0201017f010000` | `5f844776` |

**KLV 框架已验证**：
- 键 = 16 字节 SMPTE Universal Label，全部以 **`060e2b3402530101`** 开头
  （`06 0e 2b 34` = SMPTE UL 前缀，`02` = 组，`53` = 注册，`01 01` = 版本/应用）
- 长度 = **BER 编码**，这里全部用三字节长形式（`0x83 xx xx`，故长度字段占 4 字节）
- 末尾 4 个 Local Set 共用同一个 UL `…0c0201017f010000`（出现 4 次）

**两条素材的 UL 偏移逐一相同**：
`[28, 72, 96, 239, 255, 279, 489, 513, 573, 593, 984, 1008, 1024, 1048]`
（含嵌套在值内部的 UL）

## 3. 逐帧变化规律（已核对）

对比样本 0 / 1 / 2：

| 对比 | 变化区间数 | 变化字节数 | 占比 |
|---|---|---|---|
| 样本 0 vs 1 | 33 | **177 / 1064** | 16.6% |
| 样本 0 vs 2 | 40 | 177 | 16.6% |
| 样本 1 vs 2 | 46 | 177 | 16.6% |

**关键规律**：

1. **只有 1 个 Local Set 变化** —— 三个对比中变化集合都是 **Local Set[3]**
   （`0 vs 1` 和 `0 vs 2` 都是 `[3]`）。其余 5 个 Local Set 逐字节相同。
2. **变化全部落在 set[3] 的值区间内**：set[3] 的值区间 = `[513, 988)`，
   实测所有变化区间（除偏移 12 的帧计数）都在这个范围内。
3. **变化形态**：
   - `[12, 13)` —— 私有头的帧计数（见 §2.1）
   - `[625, 739)` —— **连续 114 字节**（唯一的长连续段）
   - `[755, 851)` 区间内 —— 32 个**周期性小段**
     （多为 2 字节变、2 字节不变交替，按 mod 4 分布 36–53 字节/
     每个余数，形态符合「16 位量、仅低位字节逐帧变化」）

**解读**：`cndm` 是「**固定结构 + 少量每帧状态**」的定时 metadata ——
绝大部分是静态描述（机型、镜头、录制参数），
每帧只有一小区块随拍摄状态变化（符合 IMU / 对焦 / 曝光状态的特征）。

## 4. 内部字段语义：**未解出**

**必须明确说清楚：本报告没有解出 `cndm` 里各字段的含义。**

### 已核对 ✅

- KLV 框架（16B UL + BER 长度）
- A699 首样本 6 个 Local Set 的偏移与长度
- 两条素材 UL 偏移完全一致
- 逐帧变化字节数与分布

### 未核对 ❌

- Local Set 值内部的字段语义
- 哪些字段承载 IMU / 镜头 / 对焦 / 曝光
- Canon 私有头各字段含义

### 为什么没解出（技术原因，不是没做）

对 Local Set[0]（长度 24，值 = `80000002d00080010002d7d580050002d018800600020064`）
尝试按 **SMPTE KLV 三元组**解析**不成立**：

| 检验 | 结果 |
|---|---|
| 按标准 2 字节大端标签应序列化为 | `08 00` / `08 01` / `08 05` / `08 06` |
| 实测字节 | `80 00` / `80 01` / `80 05` / `80 06` |
| 按 SMPTE 二进制标签规则 `((b0 & 0x7F) << 8) \| b1` 解 | `0x80 & 0x7F = 0` → 得到 `0x00xx` 量级 |
| 结论 | 值内部**不是**标准 KLV 三元组 |

也就是说：值和长度对得上（`80 00 00 02 d0 00` 重复四次恰好填满 24 字节，
且 `02 d0` = 720、`d7 d5` = 55253、`d0 18` = 53272、`00 64` = 100
四个值像是宽度/高度或其他度量），但**标签编码方式不符合 SMPTE 规范**，
无法仅凭字节结构确定字段身份。

**要解出语义需要**：Canon 的 XF-HEVC metadata 规范，或对已知拍摄条件的
素材做差分逆向。这超出本次调研范围。

## 5. 与 XAVC `rtmd` 的对照

| 项 | XF-HEVC `cndm` | XAVC `rtmd` |
|---|---|---|
| handler | `meta` | `meta` |
| `tref` | `cdsc` → 视频 | `cdsc` → 视频 |
| **定长样本** | **1064 B** | **19456 B**（实测，A7M5 4:2:2） |
| 样本数 | = 视频帧数 | = 视频帧数 |
| `stts` delta | 1001 | 1001 |
| 编码框架 | **KLV Local Set（SMPTE UL + BER 长度）** | Sony 私有二进制 |
| 载荷语义 | 未解出 | 未在本报告分析 |

**结论**：结构同构（定时 metadata 轨 + `cdsc` 关联 + 定长样本 + 同拍），
**载荷格式与大小完全不同**（KLV vs 私有二进制；1064 B vs 19456 B）。
两者**不能共用解析器**。

## 6. 对项目的直接影响

1. **`cndm` 目前被完全丢弃。** `core/batch_hw.py:1292` 的策略是
   「非 Sony → metadata dropped by policy（video+audio only）」，
   实测产物确实是 7 流 → 6 流，`cndm` 不在产物里。见
   `../metadata-analysis.json`。
2. **丢弃原因不是"没法保留"，而是"没有 Canon 保留管线"。**
   `cndm` 是**定长采样 + 独立轨道 + `cdsc` 关联**，
   与 Sony `rtmd` 的容器级处理方式完全同构 ——
   项目现成的 `preservation/` 机制（verbatim 轨道复制 + `tref` 重建）
   在结构上是适用的。
3. **但有一个硬障碍**：`cndm` 与视频的**耦合点**是 `tref cdsc` 到 track_id 1。
   项目重建管线已经处理过这个（`preservation/sony.py` 的 tref/cdsc 重建），
   所以不是新问题。
4. **另一个障碍是 moov 位置**：XF-HEVC 是 faststart（moov 在 mdat 之前），
   而 `preservation/isobmf.py` 的 `insert_uuid_boxes` **明确拒绝 faststart 文件**。
   若要给 Canon 做 preservation，这条必须先解决。
5. **`cndm` 语义未解出之前，即使保留轨道也只是"搬运字节"，无法验证内容。**
   建议先确认业务上是否需要 `cndm` 的内容 —— 如果只是需要保留（供后续
   工具链消费），字节级 verbatim 复制即可；如果需要读取（例如稳像），
   则必须先解 KLV 语义。
