## 2. 里程碑与验收门

### M0 — 集成基线（已完成）

- `feature/async-pipeline-p1p2` 合入 `feature/v1.0-async`；
- 短测：unit 1020/2；P1 补槽日志；P2 4ch/Sony 冒烟通过；
- 产物：本计划文档、`docs/plans/async-pipeline-and-scheduler.md`。

### M1 — 正确性缺陷修复（A2/A3/A6）

验收：

1. 透明 remux 失败回退：状态 `verify_failed`，输出仍是源文件字节拷贝（语义明确），不产生假成功；
2. 4:2:2/4:4:4 `frame_signatures` 不再抛 `IndexError`，4:2:0 结果与旧实现逐位一致；
3. 确认 `.part.mov` 残留原因；若为中间产物泄漏则清理，输出树只留最终成片；
4. unit 全绿（除既有环境项），相关新增用例通过。

### M2 — P2 资源感知（A5）

资源感知规则（实现时定稿）：

- 视频为硬件编码且 **CPU 有余量** 时，音频任务与编码并行；
- classic 路径回退软件解码、或系统 CPU 利用率过高时，音频任务**延迟到视频完成后串行执行**，不拖慢编码；
- 音频阶段仍全局串行（`Semaphore(1)`），避免 12 进程池叠加；
- 不改变最终输出，只改变时序。

验收：

- 4ch classic 软件回退素材：async wall ≤ 串行 wall（不能重现 128→149 s）；
- Sony GPU 路径：async 有收益或至少不劣化；
- 失败/中断路径不遗留音频线程。

### M3 — 调度完善（B1/B2/B4）

- **B1**：`run_multihw_pool` 改为连续补槽；全局 budget 与每后端 target 仍生效；
- **B2**：scheduler admission 时在 dashboard 建立 `queued` 行；开始后展示
  `audio/video/preserve/mux` stage；文件结束后显示 done/failed；
- **B4**：auto 调度调参，解决"长文件被补槽小文件拖慢"：
  - 按文件时长/大小排序（长任务优先）；
  - 长任务在场时限制补槽数量或给小任务短任务优先；
  - 用 7 文件基准 + 更多文件组对比总 makespan。

验收：连续补槽日志；dashboard 行覆盖全部文件；长文件组总 wall 不劣于波次基线；
`--experimental-multihw` 功能不再波次空槽。

### M4 — 评估与基线（B3/B5）

- **B3**：真实 Sony 4ch 长素材上比较 `--async-pipeline` 开/关：
  - 每文件 wall、batch wall、CPU/RSS、GPU 利用率；
  - 输出一致性（解码帧/音频/结构，不依赖压缩位流 sha；NVENC 已确认非确定）；
  - 决定 P2 是否默认、或在哪些条件下默认；
- **B5**：固化短基准脚本（7 文件 + 4ch 片段）与基线 JSON，后续回归可直接对比。

验收：评估报告 + 基线数据落盘；对 P2 默认值给出明确结论。

## 4. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| NVENC 压缩位流非确定 | 无法用整段 sha 证明输出等价 | 用解码帧 MD5、音频流 sha、结构校验作为验收口径（已实测确认） |
| 音频线程与软件解码抢 CPU | classic 素材变慢（已实测 128→149 s） | A5 资源感知，软解/高负载时改为串行 |
| channel_sync 12 进程池叠加 | CPU/内存超卖 | 全局 audio gate=1；并发只在资源允许时 |
| dashboard 110+ 行渲染 | 终端窗口滚动/可读性 | 只显示活跃+最近完成，或分页（B2 实现时决定） |
| multihw 双队列连续调度 | 逻辑复杂、死锁 | 复用单后端调度器 + 全局 budget；保留固定预算测试 |
| A4 未做 | L3 仍有 12 条环境 FAIL | 明确记录为环境项；v1.0 发布前 A4 单独完成 |
| A8 延后 | 发布需等 A4 | 版本/包构建先 dry-run，A4 后正式发布 |

## 8. 短测证据（2026-11-01）

环境：K:\1kt_work\async_test（7 个 20261025 素材 + 4ch C1305 片段）；
RTX 5070 Laptop / iGPU；NVENC + QSV。

| 项 | 结果 |
|---|---|
| unit | 1025 PASS / 2 FAIL（缺真实 Sony/DJI 语料，既有环境项） |
| A2 | `file_copied=True` 的 remux 回退返回 `verify_failed`；透明汇总计 failed，不再假成功 |
| A3 | 4:2:2 fixture `frame_signatures` 3 帧 OK；4:2:0 旧结果不变；新增 `_pix_geometry` 单测 |
| A5 | CPU busy 时 audio 任务等待 video 完成后串行执行；4ch classic async 99.4 s vs serial 128.2 s，输出一致 |
| A6 | P1b 输出目录无 `.part.mov` 残留 |
| B1 | multihw 连续补槽：`done=3`，每个完成即从对应队列补位；无波次屏障 |
| B2 | 7 文件 run 期间 dashboard rows=7，全部先由 scheduler admit；结束后 done |
| B3 | 4ch classic serial 128.2 → async 99.4 s（-22.5%）；Sony 4ch（MP4Box -splitz 精确 1800 帧）serial 32.53 → async 27.44 s（-15.7%）；两例输出视频/音频/解码抽样一致 |
| B4 | largest-first + 连续补槽：7 文件 auto 3m07s（旧 4m03s）；音频流 7/7 与基线 SAME |
| B5 | `python tests/benchmark_async.py ...` 输出 JSON；首轮 4ch async wall 107.4 s，RSS tree 2.60 GiB |

**NVENC 非确定性**：同一命令 `--jobs 1` 两次的视频压缩流不同，但抽样解码帧 MD5
相同；验收继续使用解码帧 / 音频流 / 结构校验，不使用整段压缩 sha。

**P2 默认值结论（B3）**：两类 4ch 素材（classic / Sony 保留管线）都有
15–22% 的 wall 收益且输出一致；短测仍不足以覆盖长素材、低配机、
并发 jobs、QSV 等矩阵，因此 **v1.0 保持 `--async-pipeline` opt-in**，
默认值留到 v1.1 的完整矩阵评估后再改。A5 的 CPU-busy 串行回退保证
不会重现旧版 128→149 s 的变慢路径。

## 10. GPU 音频对齐架构分支（v1.1 候选项）

> 用户 2026-11-01 指令：在不推 v1.0.0 的前提下，开展 CUDA FP32 性能测试与
> 整体音频对齐 GPU 优化架构重写；大改开新分支、每节点报告+push。

- **分支**：`feature/gpu-align-arch`（提交 `b450de6`…`ad8b2c1`，已 push）。
- **实现**：`core/gpu_align/`（backend/精度/窗级 surface/帧级 surface/
  residual/refine/session/parity），opt-in 接入 `measure_window_delays`、
  `measure_residual_curve`、`align_time_varying`、stereo 检测 prewarm。
- **默认**：全关（`KTS_GPU_ALIGN=0`）；不改变 CLI/默认输出；VERSION 0.9.0。
- **结果**（详见 `docs/design/gpu_align_ws14_report.md`）：
  - 窗级：exact 8.1×、fast 18.6×（tracked bench）；FP64 与 CPU 同窗口记录。
  - 残差：CPU 17.0 → exact 7.1 s / fast 7.3 s；1 s 曲线逐点相同。
  - long-take：C1306 CPU 115.1 → exact 47.1 / fast 57.4 s；C1305
    CPU 131.8 → exact 62.7 s；最终 raw sha256 全同。
  - 完整 channel_sync：C1306 CPU 208.8 → exact 123.1 / fast 120.5 s；
    C1305 CPU 300.9 → exact 204.7 / fast 199.6 s；4 条 audio MOV
    sha256 全同。
- **结论**：GPU 窗级 + residual 是有效收益；帧级/单窗精化目前无收益
  （保留 CPU）。fast 与 exact 都能保持最终输出一致；完整入口 fast 略快，
  long-take 单独 exact 更快。**保持 opt-in，不进入 v1.0 默认**；作为
  v1.1 候选继续评估。
- **未完成**：目标机 CuPy/CUDA 兼容矩阵、完整 L3/final_accept 新架构复验、
  GPU 帧级/精化的 no-go 正式报告、是否合并回 v1.0。
